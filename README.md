# ModelLedger

**Prove which AI model produced a file — and know when you can't.**

AI-generated content passes through many hands. An image is generated by one
model, upscaled by another, re-encoded by a publishing platform, and posted
somewhere else entirely. By the time someone asks "where did this come from?",
the file's bytes have changed and the original claim is long gone.

The usual answer is a digital signature. But a signature proves *who made a
provenance claim* — it does not prove *that the claimed model produced the
artifact*. Anyone can generate a keypair, name it "OpenAI", sign their own
claim, and present a cryptographically valid signature for something OpenAI
never made.

ModelLedger takes that gap seriously. It records provenance, anchors it so it
cannot be quietly rewritten, and then reports honestly how much of the claim is
actually corroborated — distinguishing **trusted**, **self-asserted** and
**unverifiable** provenance rather than collapsing them into "verified".

---

## The core idea

> Nothing a registrant says about themselves can make their own claim trusted.

Only corroboration from a party *other than the claimant* can: a valid
signature from a key the operator has vetted as belonging to the named model
provider. Everything else — a complete form, a plausible parameter blob, an
early timestamp — is evidence that a *claim exists and has not been edited*,
which is a strictly weaker statement.

This is enforced structurally, not by convention. A record with every field
filled in, anchored, unconflicted and perfectly formed is **capped at 74/100**
and labelled self-asserted, because no independent party vouches for it. The
cap sits one point below the trusted band on purpose.

| Verdict | Score | Meaning |
|---|---|---|
| **Trusted** | 75–100 | The named provider signed this exact record with a vetted key, and the signature still matches. |
| **Self-asserted** | 40–74 | Anchored and unedited since — but only the uploader vouches for the origin. |
| **Unverifiable** | 0–39 | Too little recorded to check, or the evidence contradicts itself. |

---

## How the score is computed

Five weighted factors, renormalised over whichever apply:

| Factor | Weight | What it establishes |
|---|---|---|
| Independent attestation | 35 | A vetted provider key signed this record. The only factor that *corroborates* rather than *records*. |
| Record completeness | 30 | Proportional to the 6 provenance fields present. Weak alone — a complete form is easy to fabricate. |
| Ledger anchoring | 15 | The claim existed at a point in time and has not been edited since. |
| Lineage integrity | 10 | For derived files: the chain of custody resolves to a registered original. Not applicable to originals, and excluded from the denominator rather than granted for free. |
| No conflicting claims | 10 | No other record claims these exact bytes came from a different model. |

Then **gates** cap the result. Gates can only lower a score:

| Gate | Caps at | Trigger |
|---|---|---|
| `UNATTESTED` | 74 | No independent corroboration. |
| `CONFLICTING_CLAIMS` | 74 | Another record claims different provenance for identical bytes. |
| `BROKEN_LINEAGE` | 74 | A derivation step's declared input doesn't match its parent. |
| `REVOKED_KEY` | 74 | Signed with a key that has since been revoked. |
| `INVALID_SIGNATURE` | 39 | A signature no longer matches the record — edited after signing, or forged. |
| `CHAIN_COMPROMISED` | 39 | Ledger integrity check failed. Anchoring proves nothing while the chain is broken. |
| `REVOKED` | 39 | The registrant withdrew the record. |

Trust is recomputed from live evidence on **every read**, never frozen at
registration. This is why revoking a key retroactively strips trust from every
record it ever signed.

## Key features

**Provenance verification** — Drop a file; it is hashed in memory and matched
against the ledger. The file is never stored.

**Transformation handling** — Re-encoding, resizing and upscaling change a
file's hash completely. Registered transformations link the new hash to the
original, so a published JPEG still resolves to the PNG it came from. A step
whose declared input hash doesn't match its parent is flagged, not absorbed.

**Multi-system provenance** — Content passing through several models carries a
chain of custody, each step naming what went in, what came out, and which
system did it.

**Tamper detection** — Each block commits to a Merkle root over the artifacts
it anchors. Editing an anchored record breaks the root; rewriting the block to
match invalidates every block above it. Five independent checks run per block.

**Privacy-preserving verification** — Prompts are **salted** and hashed, never
stored. Whoever holds the original prompt can prove it produced a record; the
ledger reveals nothing to anyone else. The salt matters: an unsalted hash of a
short prompt like *"a cat on a skateboard"* is trivially reversible by
dictionary attack, which would defeat the whole guarantee.

Merkle inclusion proofs give sibling **hashes only**, so you can prove your
artifact is in a block without learning which other artifacts share it.

**Adversarial testing** — Seven attacks run against the live engine on demand.
Nothing is mocked: real records are inserted, real keys sign, the real
validator runs. Each executes inside a transaction that is **rolled back**, so
the ledger is untouched.

| Scenario | Attack |
|---|---|
| Fabricated provider attestation | Self-minted key named "OpenAI" signs its own claim |
| Conflicting provenance claims | Identical bytes registered as two different models |
| Incomplete provenance record | A model name and nothing else |
| Record edited after anchoring | Insider rewrites an anchored row directly in the DB |
| Forged derivation link | Unrelated file claims a trusted artifact as its parent |
| Compromised provider key | A vetted key is stolen, then revoked |
| Legitimate re-encode *(control)* | Honest transformation — provenance should survive |

## Running locally

Requires Node 20+.

```bash
git clone https://github.com/workspace220106/BNB26_Ben10_Internal_Round.git
cd BNB26_Ben10_Internal_Round
```

**Backend** — port 4000:

```bash
cd backend
npm install
cp .env.example .env
npm run seed          # provisions provider keys + demo artifacts
npm run dev
```

**Frontend** — port 3000, in a second terminal:

```bash
cd frontend
npm install
cp .env.example .env.local
npm run dev
```

Open <http://localhost:3000>.

The seed writes `backend/data/demo-keys.json` (attester private keys) and
`backend/data/demo-prompts.json` (prompts for testing the privacy proof). Both
are gitignored — they are demo credentials and must never be committed.

To reset the ledger: `npm run seed -- --reset`.

## Architecture

```
backend/
  src/
    lib/crypto.js       SHA-256, salted hashing, Merkle trees, Ed25519 attestations
    lib/chain.js        Block construction, proof-of-work, 5-point chain validation
    lib/trust.js        The trust engine — weighted factors, gates, lineage, conflicts
    routes/             artifacts · transformations · attesters · adversarial · ledger
    db.js               SQLite schema, additive migrations
    seed.js             Idempotent demo seeding
frontend/
  src/app/              Home · verify · register · derive · ledger · adversarial · artifact/[id]
  src/components/       Shared console vocabulary (verdicts, hashes, evidence tables)
  src/lib/api.ts        Typed API client
```

**Stack** — Express 5 + better-sqlite3 · Next.js 16 (App Router) + Tailwind v4 ·
Node `crypto` for all primitives (no crypto dependencies).

### API

| Method | Route | Purpose |
|---|---|---|
| `POST` | `/api/artifacts/register` | Hash a file, anchor a provenance claim |
| `POST` | `/api/artifacts/preview-trust` | Project a verdict before committing |
| `POST` | `/api/artifacts/verify` | Verify by file upload |
| `POST` | `/api/artifacts/verify-hash` | Verify by SHA-256 |
| `POST` | `/api/artifacts/:id/prove-prompt` | Prove a prompt without disclosing it |
| `GET` | `/api/artifacts/:id/chain` | Full chain of custody |
| `POST` | `/api/transformations` | Register a derivation |
| `POST` | `/api/attesters/attest` | Attach a signed attestation |
| `GET` | `/api/ledger/validate` | Full chain integrity check |
| `POST` | `/api/adversarial/run-all` | Run the attack suite |

## Deployment

**Backend → Render** (blueprint included):

`render.yaml` provisions the Docker service with a 1 GB persistent disk mounted
at `/var/data`. The disk is **required** — SQLite on ephemeral storage loses
every block on redeploy. Set `FRONTEND_URL` to your Vercel URL in the
dashboard, then run `npm run seed` once from the Render shell.

**Frontend → Vercel**: set root directory to `frontend` and
`NEXT_PUBLIC_API_URL` to your Render URL.

## Honest limitations

This project is better served by naming these than by hiding them.

- **It is a single-operator ledger, not a distributed one.** The proof-of-work
  makes silent rewriting expensive and detectable; it does not provide
  Byzantine consensus. An operator who rewrites the entire chain from a tampered
  block onward would produce an internally consistent ledger. Anchoring the
  latest block hash to an external public chain would close this, and is the
  obvious next step.

- **Vetting provider keys is a human process.** The `provider` vs `community`
  distinction is the hinge the whole trust model turns on, and it is established
  out of band by the operator. No software can verify that a key really belongs
  to OpenAI; pretending otherwise would be exactly the dishonesty this project
  exists to avoid.

- **Verification is byte-exact or lineage-based.** A screenshot of a registered
  image, or a re-encode nobody registered, will not match. Perceptual hashing
  would help and the schema reserves a column for it, but it is not implemented
  — and perceptual hashes bring false-positive risks a trust system should not
  take on casually.

- **`NOT_FOUND` means nothing was registered.** It is not evidence that content
  is authentic, or that it is not AI-generated. The UI says so explicitly rather
  than letting absence read as exoneration.

- **Demo attester keys are served by the API** so the attestation flow can be
  exercised. Set `ALLOW_DEMO_KEYS=false` in any real deployment.
